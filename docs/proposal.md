## 0. 摘要

长程 agent 的上下文管理正在经历一次转向：从"对话历史就是记忆"，转到"维护一份显式状态"。

- **CLM**（2609.37725）让模型用代码随意改写自己的上下文；
- **SKILL.state**、**PoS**、**Scroll**、**VISTA** 等工作，在 2026 年 6 到 10 月间密集提出各自的状态表示。

但这个领域有五个明显的缺口：

1. 方法各用各的基准；
2. 成本只数 token，不算缓存；
3. 只报最终成功率，不知道失败出在哪一步；
4. 没有人看过"结构的收益"如何随模型变强而变化；
5. "为什么历史在事实被更正时会失败"这个机制，没有人做过因果检验。

本提案用一套共用的实验设施（同一个 agent 循环、同一套基准、按带缓存的真实成本计价、对照真值状态逐步测量），回答四个问题：

| 编号 | 问题 | 性质 | 预计产出 |
|---|---|---|---|
| **I1** | 状态的结构应该由人规定，还是让模型自己长出来？这个答案随模型规模怎么变？ | 科学问题 | 主论文的一半 |
| **I2** | 基于状态和基于历史的 agent，失败分别出在哪一类错误上？ | 测量工具 + 发现 | 主论文的另一半，外加开源工具 |
| **I3** | 历史在事实被更正后会失败：原因是新旧信息互相矛盾，还是缺少一个"唯一的真相来源"？ | 机制问题 | 短文，最快出结果 |
| **I4** | 不依赖事先写好的完整 schema，能不能在动作发生的那一刻再取回需要的事实？ | 方法 | 视 I2 结果决定做不做 |

## 1. 背景

### 1.1 CLM 做了什么

CLM 把 agent 的上下文镜像成一个文本文件，模型用 bash 或 python 任意改写，改完就是下一轮的上下文。实现见本仓库 [`clm/clm_harness`](../clm/clm_harness/README.md)。它的贡献：

- **测量**：prefix-reuse FLOPs，一种把编辑导致的重新计算也算进去的成本口径；
- **推理服务**：SCR（Suffix Cache Reuse），编辑后复用后缀的缓存；
- **学习**：ICL 技能演化，以及"只有成功的轨迹之间才比效率"的 RL。

主要结果，来自基于论文全文的第三方笔记 [N]：

| 基准 | CLM | 对比 |
|---|---|---|
| BrowseComp-Plus | 59.4% | 比最强基线高 11.4%（相对） |
| TerminalBench 2.1 | 与 Summary 持平 | FLOPs 只用了 Summary 的 70% |
| TBLite | 73.7% | Summary 67.0% |
| Qwen3.5-9B 经 RL 训练后 | 42.5% | 用同样方法训练的 Summary 是 42.1% |

**公平性提醒**：论文里只有 CLM 享有三项额外待遇——预算提醒、编辑轮不计步数、超预算回滚。本研究的对照组会统一这些待遇（§3.8）。

### 1.2 "状态派"的三条路线

详见 [文献地图](literature_map.md) 第 3 节。

1. **用状态取代历史**：SKILL.state（JSON 状态，每步打补丁）、PoS（信念状态 + 一致性校验 + 卡住后恢复）、Agent-BRACE、BeliefMem、BB-WM、From History to State。
2. **记录和视图分离**：Scroll（只追加的事件日志 + 常驻 Python kernel）、InfiAgent、ESAA、NOOA。
3. **让 prompt 的组装有依据**：VISTA（让模型看到每块记忆的使用情况）、ContextRender（按工具结果之间的依赖关系取舍）、ContextPipe（像数据库优化查询那样组装上下文）。

### 1.3 已有证据

| 证据 | 数字 | 来源 |
|---|---|---|
| 事实被更正后：显式状态 vs 完整历史 | 93/93 vs 18/82（Haiku 4.5 + Sonnet 5） | delayed-relevance 复现项目 [R] |
| 信息 40 步后才用上 | 完整历史 17%；状态里没有对应字段 0%；用到时提炼后提醒 100%；原文照搬提醒 67% | 同上 [R] |
| 知识更新题：自维护的有界笔记 vs 完整上下文 | 笔记 63/64/77，完整上下文 82/91/92 | Supersede 仓库 [R] |
| PoS 在 ALFWorld 和 LOCA 上的成绩（Qwen3.7-Plus） | ALFWorld：PoS 88.81，原始轨迹 62.69，最强基线 72.39；LOCA（7 个长度 × 75 例汇总）：PoS 56.38，原始轨迹 43.62 | PoS 仓库 `docs/results.md` [R] |
| 一算缓存，状态的成本优势缩水 | SKILL.state 的 token 优势是 7.54 倍，按实际计费只剩 1.39 倍；同样内容，可变状态放在历史前面，成本是放在后面的 5.7 倍 | delayed-relevance [R] |
| SKILL.state 在 InterCode CTF 上 | SKILL.state 54.2，带记忆摘要的 ReAct 46.4，LangGraph 有状态 agent 41.8（**这个实验里没有"状态 + 完整历史"这个设置**） | [S] |

### 1.4 这个领域的五个缺口

| 缺口 | 现状 | 对应的问题 |
|---|---|---|
| (a) 基准割裂 | 状态派在 LOCA 上比，上下文管理派在 BrowseComp-Plus 上比，两派之间几乎没有直接对比 | I1、I2 |
| (b) 成本口径 | 绝大多数论文只数 token；算上缓存后，各方法的排序会变 | 所有问题 |
| (c) 只看最终结果 | 没有对照真值、逐步定位错误的测量手段 | I2 |
| (d) 缺少规模维度 | 不知道结构的收益会不会随模型变强而消失 | I1 |
| (e) 机制未经检验 | "历史在更正时失败"的原因只是一种解释，没有被因果检验过 | I3 |

## 2. 研究问题

- **RQ1（I1）**：在同一个 agent 循环、同一组基准下，人为规定的结构（固定 schema、框架规定的信念格式），相对于模型自己长出来的结构（CLM 自由编辑、模型自己设计 schema），收益随模型规模怎么变？
- **RQ2（I2）**：基于状态和基于历史的 agent，失败主要来自哪一类错误？这个分布如何随任务的"信息需求可预测性"变化？
- **RQ3（I3）**：历史在事实被更正后失败，原因是新旧信息共存造成的干扰，还是缺少唯一真相来源这一表示层面的问题？
- **RQ4（I4）**：在动作发生的那一刻从只追加的日志里取回并提炼相关事实，能否在不需要事先写好完整 schema 的前提下，达到"状态里有对应字段"的效果，同时保持对缓存友好？

## 3. 共用实验设施

### 3.1 底座：PoS 的 agent 循环

- **代码**：[`third_party/methods/pos`](../third_party/README.md)（MIT），固定版本 `d6acb43`。
- **为什么选它**：
  - 已经接好了 ALFWorld、LOCA-Bench、RCA-100、ClinDiag；
  - 每个基准都自带原始轨迹和 PoS 两套配置，可以先复现它公布的数字，确认我们的设施没问题；
  - 上下文策略通过 `ContextProvider` 接口注入（`contexts/base.py`），只有四个方法：`reset`、`update`、`get_context`、`get_result`。原始轨迹的实现（`contexts/raw.py`）只有 45 行，加新的对照组成本很低。
- **我们自己的代码**：计划放在 `state_study/`（尚未创建），包括四部分：
  1. 各对照组的 `ContextProvider` 实现；
  2. 真值状态抽取器；
  3. 带缓存的成本统计；
  4. 错误账本和分析脚本。
- **不改动上游代码**：需要改的地方用子类或 patch 文件实现。

### 3.2 对照组

| 编号 | 名称 | 策略模型每步看到什么 | 谁来写状态 | schema 从哪来 | 保留历史吗 | 缓存布局 |
|---|---|---|---|---|---|---|
| A0 | Raw | 任务 + 完整的动作和观察历史 | — | — | 全部保留 | 只追加，对缓存最友好 |
| A1 | Summary | 任务 + 摘要 + 最近 k 步 | LLM 按阈值写摘要 | — | 被摘要替换 | 每次摘要都打断缓存 |
| A2 | CLM | 任务 + 可编辑的上下文文本 | 模型用 Python 改写 | 模型自己长出来 | 由模型决定 | 编辑点之后全部打断 |
| A3 | Schema-State | 任务 + JSON 状态 + 最新观察 | 模型输出补丁 | 人按基准写一次 | 丢弃 | 每步变，但 prompt 很短 |
| A4 | Self-Schema | 同 A3 | 模型输出补丁 | 模型在任务开始时自己设计，中途可以扩展 | 丢弃 | 同 A3 |
| A5 | PoS | 任务 + 信念状态 + 当前缺口 | 信念管理器 + 校验器 | 框架规定 | 不作为依据 | 每步变 |
| A6 | State+Log | 只追加的日志 + 放在末尾的状态块 | 模型输出补丁 | 人写（或 A4 的方式） | 全部保留 | 历史部分可以缓存，只有尾部在变 |
| 参考 | VISTA、Scroll | 各自的官方实现，只在 LOCA 上跑 | — | — | — | — |

几个实现细节：

- **A2（CLM）**：ALFWorld 和 LOCA 的循环里没有 bash 沙箱，所以提供一个 `edit_context(python_code)` 工具。渲染和解析直接复用 [`clm/clm_harness/context_utils/context_string.py`](../clm/clm_harness/context_utils/context_string.py)。
- **A3（Schema-State）**：参考 [`skill-state-runtime`](../third_party/README.md)（MIT），按 SKILL.state 的设定实现：每步输入 = 规格 + 状态 + 最新观察。**修正上游一个已知问题**：先执行动作、看到结果，再提交状态补丁（读书笔记指出 SKILL.state 是先提交后执行，失败的动作会让状态显示"已成功"）。
- **A6（State+Log）**：状态块放在 prompt 末尾。这正是 delayed-relevance 复现里测出的、对缓存友好的那种顺序。

### 3.3 基准

按"未来要用的信息能否事先预知"排列：

| 基准 | 可预测性 | 规模 | 真值状态 | 已发表可对比的数字 | 用在哪 |
|---|---|---|---|---|---|
| **仓库模拟探针**（我们自己重新实现） | 可控（参数 k、是否有更正、schema 是否覆盖） | 按需生成 | 构造时就是精确的 | delayed-relevance [R] | I3、I2 校准、I4 |
| **ALFWorld**（valid-unseen，134 局） | 高 | 每局 50 步上限 | TextWorld 的 `facts`（需打开，见 §3.6） | PoS [R] | I1、I2、I4 |
| **LOCA-bench** | 中：任务一开始就给出，但环境信息不断增长 | 8K 和 32K 各 75 例；128K 取 15 例的子集 | 环境里的模拟服务数据 + 部分任务自带的 `groundtruth_workspace` | PoS [R]、Scroll [S]、VISTA [S] | I1、I2、I4 |
| **LongMemEval 知识更新子集**（78 题，oracle 和 S 两个版本） | 低：问题在读完所有对话之后才出现 | 78 题 | 题目答案，加上标注为 `has_answer` 的证据轮次 | Supersede [R]、Scroll [S] | I1、I2、I3（自然场景）、I4 |

**不选的基准及原因**：见 [文献地图 §6](literature_map.md)。BEAM、STATE-Bench、InterCode CTF 是时间允许时的扩展选项。

### 3.4 模型

- **规模对比（I1 必需）**：同一模型家族至少 3 个规模。两个候选方案：
  - 开源权重：Qwen 3.5/3.6 系列的多个尺寸，用 vLLM 自己部署。好处是能同时算 prefix-reuse FLOPs，也能试 SCR。
  - API 分档：同一家厂商的小、中、大三档模型。
  - **待定**：取决于 API 预算和 GPU 资源。
- **上限参照**：一个前沿模型，只跑主要对照组。
- **固定设置**：temperature 0；`max_tokens` 与 PoS 的配置一致（ALFWorld 512，LOCA 4096）；所有对照组使用相同的 JSON 输出模式。

### 3.5 指标

1. **任务成功率**：使用各基准的官方判定。
2. **依赖步准确率**（探针环境）：只统计那些"正确动作取决于某条更早事实"的步骤。复现项目表明，这比按回合统计灵敏得多。
3. **成本**，三个口径同时报告：
   - 厂商实际计费（区分命中缓存的 token 和没命中的 token）；
   - 开源模型的 prefix-reuse FLOPs，复用 [`clm/clm_harness/flops_metrics`](../clm/clm_harness/flops_metrics/)；
   - 原始 token 数，用来和已发表的论文对齐。
   - **排序以前两个口径为准。**
4. **状态保真度**（I2）：每一步状态中的断言相对真值的准确率和覆盖率，以及"过时"的持续时长（真值已经变了，状态还没跟上的步数）。
5. **行为统计**：编辑次数、状态大小、schema 被扩展的次数、额外的 LLM 调用次数。

### 3.6 真值状态怎么拿

| 基准 | 真值来源 | 可行性 |
|---|---|---|
| ALFWorld | TextWorld 的 `request_infos.facts`。ALFWorld 在 `alfred_tw_env.py` 里构造 `EnvInfos`，默认不请求 facts（只有手写专家模式会打开）。PoS 的 adapter 只返回观察、可选动作和是否成功 | 要改一行配置或打一个小 patch。facts 能否稳定拿到，需要在第 1 周验证 |
| LOCA-bench | 每次工具调用后，给模拟服务的数据和工作区拍快照。先从带 `groundtruth_workspace` 的任务家族入手 | 各任务家族的接口不一样，先做 3 到 5 个家族 |
| 仓库模拟探针 | 构造时就精确知道 | 直接可用 |
| LongMemEval 知识更新 | 题目答案 + `has_answer` 证据轮次。哪一轮是"被取代的旧值"没有直接标注 | 要么人工标，要么让 LLM 标、人工抽查 |

### 3.7 日志

每一步记录以下内容：

- 实际发给模型的完整 prompt（用来回放缓存命中情况）；
- 状态快照；
- 动作和观察；
- token 用量，包括命中缓存的部分。

在 PoS 已有的 `events.jsonl` 上加字段；条件允许时，与 CLM 的 ATIF-CTX 轨迹格式兼容。

### 3.8 公平性约定

所有对照组统一以下设置：

- 步数上限、工具集合、观察截断规则、JSON 重试次数、温度；
- **任何对照组都不享有额外待遇**（CLM 论文里的预算提醒、编辑轮不计步数、超预算回滚），要么所有组都有，要么都没有；
- 额外的 LLM 调用（PoS 的校验器、I4 的召回步骤）计入成本，并单独报告。

### 3.9 统计与噪声底

delayed-relevance 复现项目的教训：它文档里至少有四个结论，在测量噪声底之后被推翻了。所以：

- **每组大实验之前先测噪声底**：选 2 个对照组 × 10 个用例，用同一个随机种子重复 8 次；
- 尽量采用配对设计（同一用例、同一种子比较不同对照组）；
- 成功率报告 Wilson 置信区间，配对比较用 McNemar 检验；
- 样本量和用例的选择规则事先写好；
- 优先选择"依赖步"多的用例：可以先不调用 API，算出每个用例里有多少步的正确动作依赖那条事实，再决定用哪些用例。

## 4. I1：结构从哪里来？人为规定 vs 模型自己长出来，随模型规模的变化

### 4.1 出发点

这一波工作里有两种相反的思路：

- **人为规定结构**：SKILL.state 的 schema、PoS 的信念格式；
- **让结构自己长出来**：CLM 自由编辑，模型会自发搭出计分板、笔记块、可复用的函数。

按照 Bitter Lesson 的逻辑，模型越强，人为结构的收益应该越小，甚至变成负担。CLM 论文也观察到"模型越强，CLM 收益越大"，9B 模型在不训练的情况下反而不如 Summary。但目前**没有人在同一个循环、同一组基准下，跨规模比较过这两种思路**。

### 4.2 假设

- **H1a**：人为结构（A3、A5）相对于自由形式（A2）的优势，在小模型上最大，并随规模增大而缩小。
- **H1b**：A2 的轨迹里自发出现"类状态结构"的比例随规模上升，而且在控制用例难度后，这类结构的出现能预测成功。
- **H1c**：模型自己设计 schema（A4）与人写 schema（A3）的差距随规模缩小，也就是说"设计 schema"本身也是一种会随规模提升的能力。

### 4.3 设计

- **实验矩阵**：A0–A6 七个对照组 × 3 到 4 个模型规模 × 4 个基准（ALFWorld 134 局、LOCA 8K、LOCA 32K、LongMemEval 知识更新 78 题）。
- **重复**：
  - 全量矩阵每个用例跑 1 次；
  - 另取 30 个用例的子集跑 3 次，用来估计方差；
  - 规模对比用配对设计。
- **如何识别"自发出现的状态结构"**：
  1. 把 A2 的每次编辑分为四类：删除、摘要、重组成状态、插入笔记；
  2. 如果某个文本块被原地更新至少 3 次，就判定为一个"持续维护的状态块"；
  3. 统计这类块出现的回合比例；
  4. 用"成功 ~ 是否有状态块 + 用例固定效应"的回归，检验 H1b。
- **schema 扩展的记录（A4）**：记录 schema 被扩展的次数和时机，以及扩展前后在依赖步上的表现。

### 4.4 预期结果与解读

| 观察到的现象 | 解读 | 对这个领域的意义 |
|---|---|---|
| 人为结构的优势随规模单调缩小 | 结构只是给弱模型的拐杖 | 对前沿模型，应该倾向于自由形式加最少的约束 |
| 优势基本不随规模变化 | 结构是独立于规模的设计收益 | 状态派的路线是长期有效的 |
| 在大模型上出现反转 | 人为结构会限制强模型 | 和 CLM 的立场一致，需要能自动扩展的 schema |
| 结果因可预测性而不同 | 结构的价值取决于任务 | 应该按任务类型来选表示方式，和 I2 的结论对接 |

### 4.5 风险与应对

- **同一家族凑不齐 3 个以上的规模**：退而用同一厂商的 API 分档，并在论文里说明这会带来的混杂因素。
- **成本**：LOCA 只跑 8K 和 32K，128K 只用 15 例的子集。
- **指令遵循能力与结构能力混在一起**：额外报告"格式错误率"，并按每个规模分别校准 prompt。

## 5. I2：状态错误账本——失败到底出在哪一步

### 5.1 出发点

现在的论文只报最终成功率。delayed-relevance 复现项目用几个人工探针才发现，真正的瓶颈是"schema 里没有这个字段"（有字段 100%，没有 0%），以及在 Sonnet 上"补丁格式合法、但语义写错了"。**目前没有一种通用的、对照真值逐步定位错误的测量手段。** I2 就是要做这个工具，并在 I1 的全部运行上使用它。

### 5.2 错误分类

先定义"依赖决策点"：某一步 d，它的正确动作取决于一条事实 f，而 f 在 d 时刻的真值是 v。每个出错的依赖决策点归入下面第一个成立的类别：

| 类别 | 定义 | 典型场景 |
|---|---|---|
| E1 没覆盖 | 从 f 第一次被观察到，直到 d，agent 的表示里从未出现过 f | schema 里没有对应字段；被摘要压缩掉了 |
| E2 写错 | f 被写入了，但写入时的值和观察到的不一致 | 补丁格式合法，但语义抄错 |
| E3 过时 | f 之前写对了，后来真值变了，到 d 时还没更新 | 漏掉了一次更正 |
| E4 没用上 | d 时刻的表示里有正确的 v，但动作和 v 不一致 | 历史里新旧信息都在，模型用了旧的 |
| E5 没取回 | v 在日志里，但到 d 时没有被取进上下文 | Scroll、I4 这类"从日志里取"的方法 |
| 其他 | 无法归到某条具体事实的推理或规划错误 | — |

### 5.3 怎么操作化

- **找出依赖决策点**：
  - 探针环境：构造时就已知；
  - ALFWorld：用动作的前置条件（对象的位置、状态）和 facts 的变化来确定；
  - LOCA：从真值工作区反推出需要哪些事实。这一步较难，先用 LLM 标注，再人工抽查 100 个，报告标注准确率；
  - LongMemEval 知识更新：f 就是被更新的那个属性，d 就是回答问题的那一刻。
- **从表示里提取断言**：
  - 结构化的对照组（A3–A6）直接读状态；
  - 文本形式的对照组（A0–A2）用 LLM 提取，并在人工标注的子集上报告提取器的准确率。
- **输出**：
  - 每个对照组 × 每个基准的错误构成堆叠图；
  - 错误构成随"可预测性"的变化；
  - 错误构成随模型规模的变化（与 I1 联动）。

### 5.4 假设

- **H2a**：在信息需求不可预测的任务上，状态类对照组以 E1 为主；在强模型上，E2 的占比上升。
- **H2b**：历史类对照组在有更正的场景里以 E4 为主（新旧信息共存，模型用了旧的）；在压缩类对照组里以 E1 为主。
- **H2c**：错误构成能解释各篇论文之间看似矛盾的结论。例如在 Supersede 里笔记输给完整上下文，应该对应 E1 占主导。

### 5.5 产出

- 一个开源的"状态错误账本"工具包：输入轨迹和真值，输出逐步的错误归因；
- 论文的核心图：哪种失败、在哪类任务、被哪种表示方式消除。

### 5.6 风险

- **标注成本**：探针和 ALFWorld 可以全自动；LOCA 和 LongMemEval 先做子集。
- **提取器本身出错**：报告人工核对的准确率；对于结构化对照组，不使用 LLM 提取。

## 6. I3：新旧矛盾，还是缺一个唯一的真相来源？

### 6.1 出发点

delayed-relevance 复现里，事实被更正后，显式状态 93/93 次都用对了，而完整历史只对了 18/82 次。作者的解释是："历史不会删掉任何东西，它把原记录和更正都留着，后面每一步都要重新判断信哪个。"**这个解释没有经过因果检验。**

两种解释的工程含义截然不同：

- **如果是干扰造成的**：保留历史、但给旧条目做清理或标注就够了，还能保住缓存优势；
- **如果是表示方式造成的**：必须有一个唯一的真相来源。

### 6.2 实验条件

同一个环境种子、同一段轨迹前缀，只改变上下文的处理方式：

| 条件 | 处理方式 | 检验什么 |
|---|---|---|
| T0 | 原始历史 | 基线 |
| T1 | 由 harness 给被取代的条目标注"已被第 t 步更正"（标注完全正确） | 只告诉模型"这条过时了"，够不够 |
| T2 | 由 harness 直接删掉被取代的条目（删除完全正确） | 去掉干扰源，够不够 |
| T3 | 由模型自己用 CLM 编辑来识别并删除 | 和 T2 的差距 = 模型识别更正的代价 |
| T4 | 显式状态（A3） | 唯一真相来源 |
| T5 | 显式状态 + 完整历史 | 在状态旁边加上历史，会不会反而干扰。这正是之前误读的那个结果，这次正式测量 |

### 6.3 环境

- **主要环境：仓库模拟探针**。依据 SKILL.state 论文 §4.1 对仓库任务的描述**重新实现**；delayed-relevance 的代码没有 license，只参考它的设计，不复用代码。可调参数：
  - 事后更正：例如在 t+10 步通知"之前那次放置其实没完成"；
  - 延迟相关：一条信息在 k 步之后才用上，k ∈ {1, 5, 10, 20, 40}；
  - 干扰信息的密度。
- **自然场景**：LongMemEval 知识更新子集，跑 T0、T2、T4 三个条件。T2 需要先标出哪一轮是被取代的旧值（见 §3.6）。

### 6.4 设计与指标

- **配对设计**：同一个种子重复 8 次；2 个模型（一小一强）；先测噪声底。
- **主要指标**：依赖步准确率。
- **次要指标**：带缓存的实际成本。T1 只在末尾追加标注，不破坏缓存；T2 和 T3 的删除会打断缓存。
- **用例选择**：按每个种子"有多少步依赖这次更正"来挑，避免像复现项目早期那样，选中的种子里根本没有可测的步骤。

### 6.5 预期结果与解读

| 结果 | 解读 |
|---|---|
| T1 ≈ T2 ≈ T4，都远高于 T0 | 问题出在干扰。保留历史并做标注或清理就够了，标注还对缓存友好 |
| T4 远高于 T1 和 T2 | 问题出在表示方式，需要唯一真相来源 |
| T3 明显低于 T2 | 瓶颈在于模型能否识别出"这是一次更正" |
| T5 低于 T4 | 在状态旁边加上历史会造成干扰，A6 这种布局需要谨慎 |

### 6.6 时间与产出

2 到 3 周，产出一篇短文或 workshop 论文，抢先占住时间戳。代价最小，结论也最干净。

### 6.7 冒烟测试结果（2026-10-03）与修订后的设计

**已经完成的部分：**
- 探针环境、全部渲染条件和打分脚本已实现：`state_study/probes`；
- 19 个单元测试通过：确定性、每个决策都依赖关键事件、独立重新模拟得到的真值一致、规则读者只看文本就能答对；
- 用 Haiku 子 agent 跑了 36 题的冒烟测试，详见 [`state_study/pilots/2026-10-03_haiku_smoke`](../state_study/pilots/2026-10-03_haiku_smoke/README.md)。

**观察到的现象（n=3，只说明方向）：**
- `state_noq` 0/3，全部是"忽略关键事件"式的错误；
- 原始历史 6/9。它的 3 个错误里只有 1 个是用了旧值，另外 2 个是从 270 多步的日志里重建状态时出错。

**据此修订假设：历史的失败可以拆成两种相互独立的机制**

| 机制 | 含义 | 什么能修复它 | 怎样单独测量 |
|---|---|---|---|
| **M1 干扰** | 被作废的旧条目和更正同时存在，模型用了旧的 | 只追加的作废清单（`tomb_tail`），或删除旧条目 | 对比 `raw` 和 `tomb_tail`、`delete` 的差距 |
| **M2 重建负担** | 当前状态需要从很长的日志里推出来；日志越长越容易错，和有没有更正无关 | 只有显式状态（`state`，或把状态附在末尾的 `state_log`） | 新增一种**没有任何更正、但答案取决于大量出入库累积结果**的对照场景（`control`），单独测重建错误率随日志长度的变化 |

**可证伪的预测：**
- 如果 M1 占主导：`tomb_tail` 接近 `state`。那么"丢掉历史、换成状态"就是过度设计，保留缓存和可审计性的作废日志就够了。
- 如果 M2 占主导：只有状态类条件能稳定答对。但 `state_log`（保留历史、状态放在末尾）应当不比 `state` 差，也就是说可以不丢历史。

两种结果都能落到可操作的结论上，这也是这个问题有张力的原因：它直接检验这一波"用状态取代历史"论文所依赖的前提。

**为避免天花板（冒烟测试里原始历史仍有 67% 正确），正式设计做以下调整：**
- 日志长度：gap 取 {20, 60, 160, 320}，warm-up 增加到让带历史的提示达到 3 万 token 以上；
- 每个场景里被作废的条目数取 {1, 3, 10}；
- 新增 `control` 场景，单独测量 M2；
- 新增 `state_head` 条件（状态放在日志前面），量化状态放置位置对缓存成本的影响；
- 增加多轮模式：模型自己执行整个回合，之前的动作由模型自己做，错误会累积，用来检验单题结论能否推广。

**正式实验规模：**
- 4 种场景 × 约 7 个条件 × 4 个 gap × 25 个种子 ≈ 每个模型 2800 题；
- 平均约 1.5 万 token，约 4200 万输入 token / 模型（未计缓存）；
- 3 个模型约 1.3 亿。
- 不需要 GPU，有 API 密钥即可在一周内跑完。

## 7. I4（方法）：在动作发生的那一刻再取回需要的事实

### 7.1 出发点

复现项目里最大的效应来自覆盖率：

- 状态里有对应字段：100%；
- 没有字段：0%；
- 加一个通用的 notes 字段：约 21%；
- 在用到时把那条事实提炼后放到眼前：100%；直接原文照搬：67%。

所以问题可以简化为：**不靠事先写好的 schema，怎么在用到的时候拿到对的事实，并且是提炼过的形式。**

### 7.2 方法（暂名 Bind-at-Act）

1. **日志**：只追加，前缀可以完整缓存。
2. **尾部状态**：一个小的状态块，由模型维护，存放可以预见的信息（同 A6）。
3. **动作时刻召回**，每一步分三小步：
   - 模型先提出一个候选动作；
   - harness 抽出这个动作涉及的实体和参数（比如货架编号、文件名、客户 ID），在日志里按实体建的结构化索引里检索相关事件，先不用向量检索；
   - 把检索结果提炼成不超过 N 个字段，放到上下文末尾，模型再确认或修改动作。
4. **成本**：每步多一次调用。完整计入成本，并和"只在动作涉及很久以前见过的实体时才召回"的省钱版本做比较。

### 7.3 消融

- 去掉召回，等同于 A6；
- 召回但不提炼，直接原文放入；
- 召回并提炼；
- 只在相关实体已经很久没出现时才召回；
- 由模型自己决定是否召回 vs 每步都召回。

### 7.4 对比与基准

- **对比**：A0、A3、A5、A6；在 LOCA 上加 Scroll 和 VISTA。
- **基准**：仓库探针、ALFWorld、LOCA 8K 和 32K、LongMemEval 知识更新（"动作"就是回答问题）。

### 7.5 假设

- **H4a**：在不需要理想 schema 的前提下，显著减少 E1（没覆盖）类错误。
- **H4b**：日志只追加，所以带缓存的实际成本不高于 A3。
- **H4c**：收益主要集中在 I2 账本里被归为 E1 的那些失败上，可以用账本直接检验。

### 7.6 风险与是否继续做的判断

- **撞车风险**：思路和 Scroll（模型写代码查询）、ContextRender（按依赖关系取舍）、通用的 agent RAG 都接近。新意必须落在三点上：在动作发生时绑定、对缓存友好、用错误账本支撑分析。动手前要重新做一次撞车检索。
- **是否继续**：只有当 I2 显示 E1 在至少两个基准上是主导错误时，才继续做 I4。

## 10. 资源与预算

### 10.1 代码与数据

- **代码**：全部在 [`third_party/`](../third_party/README.md)，用 `scripts/setup_third_party.sh` 初始化。
- **需要自己下载的数据**：
  - LongMemEval（Hugging Face 或 Google Drive）；
  - ALFWorld（GitHub release 上的压缩包，已验证可以下载）。
- **LOCA**：数据在本地生成，需要 Node.js、npm 和若干 MCP 可执行程序（见 PoS 仓库的 `benchmarks/LOCA-Bench/README.md`）。
- **网络**：当前云环境拦截了 arxiv 和 huggingface。要么把这两个域名加进白名单，要么在本地机器上跑实验。

### 10.2 token 粗估

下表是每个对照组、每约 100 个用例、**未命中缓存**的输入 token，来自基准调研时的估算，只用于数量级判断：

| 基准 | 估算 |
|---|---|
| LOCA 8K–32K | 约 2500 万到 7500 万 |
| LOCA 128K 及以上 | 2 亿以上 |
| ALFWorld | 约 500 万到 1500 万 |
| LongMemEval 知识更新（78 题） | 约 300 万到 1000 万 |

**总量公式**：对照组数 × 模型数 × Σ（各基准的 token）× 重复次数。

**示例**：7 个对照组 × 3 个规模 × （ALFWorld 1000 万 + LOCA 8K 2500 万 + LOCA 32K 5000 万 + 知识更新 500 万）≈ **19 亿输入 token（未计缓存）**。只追加的对照组可以命中大约 80% 的缓存（delayed-relevance 实测）。

**建议的削减方式**：

- LOCA 32K 只跑 A0、A2、A3、A5 四个组；
- 最大的模型只跑主要对照组；
- LOCA 128K 只用 15 例的子集。

具体数额要等选定模型和价格之后再算。

### 10.3 GPU（可选）

- 用开源权重做规模梯度、计算 prefix-reuse FLOPs；
- 试 SCR：只支持 SGLang 0.5.16 + Qwen3.6-27B 单卡，用来验证"缓存 vs 编辑"的冲突能否在推理服务端缓解。
