## 1. 共同问题和总趋势

长程 agent 跑上几百上千步以后，所有信息都堆在对话历史里，会出三类问题：

- **放不下**：超出上下文窗口
- **找不到**：关键事实被淹没；旧事实和后来的更正混在一起
- **被带偏**：自己犯过的错误留在上下文里，影响后续决策

这一波工作的共同判断是：问题不在压缩得不够，而在"拿对话历史当记忆"这种表示方式本身。agent 的记忆单位正从**对话记录**换成**状态**。研究重心随之从"历史怎么删、怎么压"，变成四个问题：

1. agent 现在应该知道什么
2. 这些知识放在哪里
3. 谁来写
4. 写错了怎么办

## 5. 趋势

1. **表示方式比压缩率更重要。** 运行时的实现细节往往比方法本身影响更大（delayed-relevance 复现；NOOA 的 253 行实现）。
2. **状态的优势在于真相只存一处。** 遇到事实被更正时尤其明显。
3. **状态的上限取决于两件事：schema 里有没有那个字段，以及值写得对不对。** 未来要用什么信息事先无法预测时，状态反而不如完整上下文。
4. **成本要按缓存算，评测要按逐步真值算。** 可变状态会打断缓存；评测正在转向对照真值状态的逐步测量。
5. **出现了两个主战场。** 状态派在 LOCA-bench 上比（PoS、Scroll、VISTA），上下文管理派在 BrowseComp-Plus 上比（CLM、VISTA、ACM、SelfCompact、ContextPilot）。VISTA 横跨两边。

## 6. 基准可用性

| 结论 | 基准 |
|---|---|
| **用** | LOCA-bench（MIT，数据本地生成，有真值）、ALFWorld（MIT，有真值）、LongMemEval 的知识更新子集（数据需自行下载）。另外自己重新实现一个仓库模拟环境，用来做可控探针 |
| 备选 | BEAM 的 128K / 1M 档、STATE-Bench、InterCode CTF、τ-bench、AppWorld、RCA-100 |
| 不用 | StateMemBench、WorldLines、BeliefShift、SkillExecBench（都未发布）；DreamBench-SWE（评分标准不公开）；MemoryAgentBench（数据只在 HF，且没有可对比的方法）；CooperBench（harness 固定，和本课题无关） |
