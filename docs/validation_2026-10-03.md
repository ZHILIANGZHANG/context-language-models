# 验证报告（2026-10-03）：显式状态到底赢在哪里

> **一句话**：上一轮提出的"状态是用干扰换持久"大半没有通过验证。验证中发现了两件更重要的事：
> 1. 被反复引用的"事后更正时显式状态 93/93、完整历史 18/82"，主要是探针本身自相矛盾造成的；
> 2. 对"到达时不需要动作、之后才变得关键"的信息，两种表示以同一种方式失败。决定成败的是**信息到达时有没有被写进 agent 之后做决定会看的地方**，而不是用状态还是用历史。
>
> 修正后的论点：**决定成败的是到达时的写入，不是表示方式。** 目前的证据是方向性的，下一步需要 API 密钥做确认实验（预算估计见 §5）。

## 1. 原论点的验证结果

上一轮提出的论点有四个可证伪的子主张（C1–C4），外加一条动机证据。逐条结果：

| 子主张 | 结果 | 依据 |
|---|---|---|
| C1 干扰律：历史类表示的错误率随版本深度（被取代的旧值个数）上升 | **不成立**（至少在约 1 万 token、25 个版本以内） | 版本深度探针 18/20，错误不随深度增加（§2.7） |
| C2 持久律：状态错误的寿命由重新观察频率和采纳率决定；响亮错误会很快被纠正，静默错误活得久 | **一半成立**："持久"和"采纳率低"成立；"响亮错误很快被纠正"不成立 | Haiku T=200：错误信念中位持续 24 步，46 个里 15 个到结束都没修好；被拒后修好 8/78；会被拒的错误同样持续很久（§2.8） |
| C3 交叉点可以事先预测 | **无法检验** | 输入之一（C1 的干扰）在可测范围内接近 0；用来说明"状态赢"的标志性证据又是探针伪影（§2.2、§2.7） |
| C4 规模会移动交叉点 | **只有零散证据** | Sonnet 的状态错误很短（中位 1 步）；L1 上 Sonnet 历史 8/24，好于 Haiku 的 0/24。但两档模型都没有消除失败（§2.4、§2.8） |
| 动机证据："事实被更正时显式状态胜出"（93/93 vs 18/82） | **主要是探针伪影** | 更正通知与历史矛盾，6/6 个用过的种子都如此；只改一个字段后，历史从 4/12 升到 10/12（§2.2、§2.3） |

另外，上一轮中途提出的"整合门控"假设（动作导向的说明书让历史 agent 跳过整合）**在短上下文里不成立**：历史 24/24 全对（§2.7）。但在长距离、高密度的真实轨迹里，同类失败确实存在，而且失败点可以精确定位（§2.4–§2.6）。

### 2.2 L2 事后更正探针自相矛盾 [R]

**探针的设计**（delayed-relevance 的 `_plant_invalidation(k=10)`）：

- 选第一个"入库到当时最低空位"的步骤，几乎总是第 0 步、货架 0；
- 第 10 步发出通知：`corrects_step=0 | shelf=0 | finding=putaway_never_completed | shelf_is_now=empty | stock_removed=true`；
- 环境把货架 0 清空。

**问题**：它没有检查第 0 步那托货此时是否还在货架上。用它自己的环境跑 oracle 策略（`dr_coherence.py`）：

- 种子 0–39 中，36 个的通知与历史矛盾；
- 它的 L2 实验用过的 6 个种子（0、1、2、4、6、10）**全部矛盾**：
  - 第 0 步那托货早已发出；
  - 其中 5 个种子的货架 0 上已经放了另一托货，分别在第 8、6、4、4、8 步放入；
  - 种子 2 的货架 0 本来就空，所以没有任何依赖步。

于是环境清掉的是一托和通知无关的货。

- **历史 agent** 看得到时间线，常推理成"货架 0 上是第 8 步放的 SKU-D，之后没有被清空，所以仍然占用"（译自原轨迹里的推理），于是被判错；
- **状态 agent** 看不到时间线，照通知清空，于是被判对。

原轨迹里"第一个依赖于更正的决策"的正确率：

| 模型 | ReAct（完整历史） | SKILL.state（显式状态） |
|---|---|---|
| Haiku 4.5 | 1/24 | 24/24 |
| Sonnet 5 | 9/24 | 22/24 |
| Gemini 3 Flash | 0/24 | 24/24 |

delayed-relevance 自己的文档把这个结果解释为"历史要在每一步重新解决矛盾"、"Sonnet 更常调和这个矛盾"。但这个矛盾来自通知本身不成立，不是历史表示的缺陷。

### 2.3 一字段修正后的重放 [P]

**方法：反事实轨迹重放**

1. 取原始 Haiku ReAct 轨迹的前 10 步。模型自己写的推理原样保留。
2. 只改通知里的一个字段：`corrects_step` 从 0 改成货架上那托货实际的入库步。其余文本逐字不变。
3. 第 10 步（回应通知）和第 11 步（下一托入库，正确答案是货架 0）各让一个 Haiku 子 agent 作答。第 11 步的历史里接上它自己第 10 步的回答。
4. 种子 4、6、10，每个种子 4 条原始轨迹，共 12 个回合。

| 条件 | 第 11 步放到货架 0（正确） |
|---|---|
| ORIG：原通知 | 4/12 |
| **COH：只把通知改成与历史一致** | **10/12**（相对 ORIG，Fisher p=0.036） |
| INT：原通知 + 一句"每个事件都要更新占用记录" | 8/12 |

**两点保留**：

- **代理校准不好**：同样的原通知，原 API 轨迹是 1/24，子 agent 是 4/12，子 agent 偏"不聋"。所以这一项的证据强度弱于 L1。
- **样本不完全独立**：同一种子的 4 个回合共享同一段环境事件，12 个样本并不独立。

### 2.4 延迟相关的约束：两种表示同样失败 [R]

**L1 探针**（delayed-relevance v3 "estricto"）：

- 第 t−40 步来一条 `facility_notice`：货架 S 隔离，`do_not_store=true`。说明书里没有这种事件。
- 第 t 步，S 第一次成为最低空位，正确动作是跳过 S。
- 这个探针没有 L2 那样的矛盾：通知与历史一致，生成器检查过它是第一次起作用。

原轨迹里第一个决策的正确率（每格 24 个回合）：

| 模型 | 历史 | 历史 + 提醒¹ | 状态（无对应字段） | 状态 + 专设字段² | 状态 + 自由字段³ |
|---|---|---|---|---|---|
| Haiku 4.5 | **0/24** | 23/24 | **0/24** | 24/24 | 10/24 |
| Sonnet 5 | 8/24 | 20/24 | 7/24 | 20/24 | 10/24 |
| Gemini 3 Flash | 0/24 | 17/24 | 0/24 | 16/24 | 1/24 |

1. 通知之后的每个观察前面都加一行 `STANDING NOTICE | shelf=S | status=quarantined | do_not_store=true`。这是环境给的 oracle 提醒。
2. schema 里预先有"隔离货架"字段（oracle）。
3. schema 里有一个通用的备注字段，由模型自己决定写不写。

**注意**：`research_log` §3.2 记的"Haiku 完整历史 17%（2/12）"来自更早的版本。v3 轨迹重新统计是 0/24。

### 2.5 失败点在到达时的写入 [R]

**状态 agent**：把"状态 + 自由字段"的回合按"通知到达那一步的补丁里有没有记下隔离"分开（启发式正则判断，需要人工复核）：

| 模型 | 到达时记下了 → 决策正确 | 没记下 → 决策正确 |
|---|---|---|
| Haiku 4.5 | **10/11** | 0/13（Fisher p=6e-6） |
| Sonnet 5 | **8/9** | 2/15（p=5e-4） |

**历史 agent**：在通知那一步，回答几乎都是"facility_notice 不是程序规定的事件类型，是管理性元数据，Wait"。之后它每一步的推理只按"当前占用"推算最低空位，从没再提隔离。

可见两种表示的决策本身都没问题；**信息一旦在到达时被写下，几乎总能用上；没写下，就几乎用不上。**

### 2.6 读取时补救无效，到达时绑定有效 [P]

**方法**：用 L1 的真实 Haiku 轨迹做重放。种子 0、3、6，每个种子 4 条轨迹，共 12 个回合。通知与决策之间都是 40 步，每步约 400 token，整段约 2 万 token，保留模型自己的原始推理。

| 条件 | 做法 | 正确 |
|---|---|---|
| BASE | 原样 | **0/12**（原 API 轨迹 0/24，代理校准良好） |
| CHECK | 说明书里加一句通用提示："行动前回看整段历史，找出会改变当前正确动作的早先事件，包括当时不需要动作的事件"。不提事件类型和货架 | **0/12** |
| FACT | 把通知改写成占用事实："货架 S 被维修设备占用"。这属于 agent 一直在跟踪的占用信息，后果相同 | **0/12**，12 个决策都没提到这条通知 |
| JIT | 决策那一步的观察前加环境的提醒行（oracle） | **11/12** |
| **PIN** | 说明书提供"钉住"机制：遇到会影响以后动作的规则或限制，写一行 `PIN:`。runtime 在之后每个观察前重放钉住的行。两次调用：通知那一步一次，决策那一步一次 | 通知那一步 **12/12 都钉了**；决策 **12/12 正确**，12 个决策都引用了钉住的那一行 |

从这组重放可以读出三点：

1. 信息就在上下文里，模型也被明确要求回看，仍然 0/12。读取时的检索在相隔 40 步、约 2 万 token 的高密度上下文里基本失效。
2. 改写成占用事实也没用。所以分界线**不是**"前瞻性约束 vs 回顾性事实"，而是"到达时有没有被整合进 agent 的工作记录"。这一点和 TriggerBench 的"前瞻性记忆难、回顾性记忆易"[S] 不同，需要对照它的原文定义。
3. 不知道哪条事件重要的情况下，模型自己钉住就完全修好了。

**保留**：

- 重放不是闭环。通知与决策之间那 39 步的回答是原轨迹里的（它们从没提到通知）；真实闭环里 agent 会看到钉住的行，可能会多钉、漏钉，或者把钉住的行删掉。
- PIN 的写法提到"规则或限制"，可能对这个探针有利。FACT + PIN 还没测。

### 2.7 短上下文下，历史对更正很稳 [P]

**整合门控探针**（`ig.py`，本仓库自写）：

- 36 步、每步约 75 token、整段约 3 千 token、没有审计字段块；
- 更正通知（与历史一致）在决策前 1 步；
- 两次调用的闭环：通知一次，下一托入库一次。

| 条件 | 下一托放对 |
|---|---|
| 历史，说明书覆盖了更正事件 | 8/8 |
| 历史，说明书没覆盖、并要求"只看规定字段" | 8/8（回答里称之为"元数据"，但都承认货架空了） |
| 同上 + 整合提示 | 8/8 |
| 状态，说明书没覆盖、并要求只看规定字段 | 7/8（1 个错误：货架 0 空缺时，JSON 里漏看了最低空位） |

其他 pilot 的样本更小：

- 版本深度：同一货架最多翻转 12 次（25 个版本），18/20，看不出随深度变化；
- 事后更正 vs 事先更正、更正后的自我复述：全对，但每格只有 1–2 题。

**解读**：信息离决策近、上下文不长时，历史 agent 会主动整合。L1 的失败需要两个条件同时满足：**距离远，且到达时没写下**。

### 2.8 显式状态的代价：写错了会一直错 [R]

数据：delayed-relevance 的 SKILL.state 闭环轨迹。用环境重放执行过的动作和模型自己的补丁，逐步比较信念与现实（`dr_persistence.py`、`dr_adoption.py`）。

- **错误信念持续很久**（Haiku，T=200）：
  - 46 处"以为空、其实占用"，中位持续 24 步，15 处到结束都没修好；
  - 24 处 SKU 记错，中位持续 15 步，20 处到结束都没修好。
- **纠错反馈很少被采纳**：环境回复 `ACTION REJECTED` 并点名那个货架后，下一次补丁修好信念的只有 **8/78**。
- **错误信念的来源**：51/70 来自动作本身错了，19/70 来自动作对、补丁写错。
- **规模有影响**：Sonnet 的信念偏差都很短，中位 1 步。
- **错误成串**：所有 runtime 里，P(错 | 上一步错) / P(错 | 上一步对) 都在约 6（ReAct）到 13–14（有状态的 runtime）之间。所以"读取错误是一次性的"（H2 的一部分）不成立。

## 3. 修正后的论点

### 3.1 论点："到达时绑定"

1. **决定一条信息以后能不能被用上的，是它到达时有没有被写进 agent 之后做决定会看的地方**：状态里的槽、自己的运行摘要、钉住的笔记。
2. **显式状态赢的地方，来自 schema 对槽内信息强制做到达时写入**。L2 的更正正好落在 `shelf_contents` 这个槽里，所以状态 agent 必然写；历史没有任何机制强制它整合"现在不需要动作"的事件。**对槽外信息，两者以同样的方式失败**（L1：0/24 对 0/24）。
3. **读取时的补救救不回来**：通用的回看指令 0/12，改写成槽内事实 0/12。**到达时绑定**（agent 自己钉，12/12）或**决策时投递**（提醒，11/12）有效。
4. **强制写入的代价是强制持久**：写错了的状态持续很久，纠错反馈很少被采纳。反过来，历史保留了裁决矛盾所需的证据：L2 里通知与历史矛盾时，是历史 agent 看出了矛盾。

### 3.2 和主线、I1–I4 的关系

主线问的是"写入时付代价，还是读取时付代价"（[research_line.md](research_line.md)）。初步答案：对"到达时不可行动、之后才关键"的信息，读取时付代价在当前模型上基本无效，写入时付代价有效；**表示方式只是决定了哪些信息会被强制写入**。主线不用推翻，H1–H5 需要改写成"写入时机 × 写到哪里"的形式。

| idea | 这次验证带来的变化 |
|---|---|
| I2 错误账本 | §2.5、§2.6 正是"写入错误 vs 读取错误"的分解，并且有了因果证据（反事实重放），不只是相关 |
| I3 新旧矛盾 | 原来的动机（18/82）站不住。真问题变成"通知与历史冲突时谁来裁决"：状态 agent 看不到证据，只能照写；历史 agent 能裁决，但可能裁错。探针必须加一致性检查，并把"有效更正 / 过时通知 / 冲突通知"作为独立因子 |
| I4 动作时刻召回 | 通用的回看指令无效（0/12），必须在决策时把信息送到眼前（JIT 11/12），或在到达时钉住（PIN 12/12）。这和上一轮 pilot 里"召回目标货架 0/3 → 3/3"一致 |
| I1 结构来源 × 规模 | 专设字段（24/24）> 自由字段（10/24）≈ 写不写看运气；agent 自己钉 12/12。规模：Sonnet 在自由字段上和 Haiku 一样，都是 10/24 |

### 3.3 推荐的论文形态

**分析型论文。** 暂定题目："Rethinking explicit state for long-horizon agents: it is the arrival-time write, not the representation"。

贡献清单：

1. **仪器批评**：指出"状态胜于历史"的标志性证据（事后更正）来自自相矛盾的探针，给出一致性检查工具，以及修正后的结果。
2. **共同失败点**：在同一组延迟相关探针上，历史与显式状态都失败在到达时的写入。用反事实轨迹重放给出因果证据：改一个字段、加一个钉子，结果翻转。
3. **读取时补救无效、到达时绑定有效**：回看指令、改写成事实都失败；钉住和投递成功。
4. **强制写入的代价**：错误信念持续、纠错反馈采纳率低、错误成串；随模型规模变化。
5. **基准与方法学**：一个把"延迟相关 × 更正是否一致 × 通知是否过时"作为独立因子的生成器，带真值和规则读者测试；以及反事实轨迹重放这种低成本的因果诊断方法。

**不推荐写成"钉子方法"的方法型论文**：这个方向在 2026 年已经很挤（§3.4）。钉子在本文里只作为最小干预和基线。

| TriggerBench（2606.23459） | 前瞻性记忆比回顾性记忆难：同样上下文下回顾性记忆到 100K 仍接近满分，前瞻性记忆随长度明显下降 | 我们的 FACT 结果提示分界线是"到达时是否整合"，需要对照它的回顾性记忆的定义 |
| Typed Intention Stores / PIS（2609.01272） | 把意图生命周期放进代码；PM-Bench 上 DeepSeek-Chat 82.9% | 和 PIN 同类，是方法上的直接竞争者 |
| **Delivery, Not Storage**（2607.20972） | 编码 agent 的"以提示为锚的工作记忆"，标题即"投递，而不是存储" | **最接近**：与 JIT/PIN 的结论同向。必须读原文，确认它是否已经讨论状态 vs 历史 |
| When Should Agents Check External State?（2609.37125） | 为已存意图分配观察预算 | 相邻 |
| Did You Forget What I Asked?（2603.23530） | LLM 的前瞻性记忆失败 | 相邻 |
| Learning What Not to Forget（2606.20954） | 写入时淘汰必须在需要它的查询出现之前决定；学一个 KB 级打分器 | 与"写入时付代价"同框架，角度不同（淘汰 vs 绑定） |
| SKILL.state 原文（2608.26263） | "静默漂移时状态 0 步恢复、历史 5–8 步" | 需要读原文，看漂移实验是否也有 L2 那样的一致性问题 |

**区分点**：根据目前看到的摘要，没有一篇把显式状态 runtime 和历史 runtime 放在同一个延迟相关探针上比较；也没有人指出 L2 探针的矛盾。这两点是本文最独特的部分。

### 3.5 风险

- **代理**：所有重放都用 Haiku 子 agent。L2 的代理校准不好（4/12 vs 原 API 1/24）。必须用 API 重做。
- **重放不等于闭环**：PIN 在闭环里可能多钉或漏钉。
- **领域单一**：只有合成仓库，需要第二个领域。
- **启发式判断**：§2.5 的"记下了"是正则判断，需要人工复核。
- **撞车**：如果 *Delivery, Not Storage* 已经讨论了状态 vs 历史，贡献就收缩到仪器批评、反事实重放和基准。

## 4. 方法学上的教训

1. **探针要做一致性检查**：生成器要验证通知的说法和历史一致，否则模型"答错"可能是在正确地拒绝一个错误的通知。已有脚本：`dr_coherence.py`。这是本仓库"新领域的探针必须配规则读者测试"那条规矩的延伸：除了检查"只看文本能答对"，还要检查"文本内部不自相矛盾"。
2. **反事实轨迹重放**：用真实闭环轨迹的前缀，改一个字段，在决策点重新提问。成本极低，能给出因果证据。
3. **代理必须校准**：每组重放都要有一个"原样"格，和原 API 行为对比。L1 校准良好（0/12 vs 0/24），L2 不好（4/12 vs 1/24）。
