## 1. 一句话论点

agent 选择怎么表示记忆，本质上是在选择**什么时候付代价**：

- **保留历史 = 读取时付代价。** 信息一点不丢，但每一步都要从日志里重新推出当前状态，这一步会出错（**读取误差**）。
- **维护状态 = 写入时付代价。** 读取几乎免费，但写入时就决定了留什么：schema 里没有的东西永久丢失，写错的值会一直错下去（**写入误差**）。

哪种表示方式更好，取决于这两类误差在具体任务上谁更大。这是**可以测量、也可以事先预测**的。

## 2. 为什么这条线最有 insight

1. **能统一解释文献里互相矛盾的结论**（证据详见 [research_log.md](research_log.md) §3）：
   - **SKILL.state、PoS 里状态赢**：任务是程序性的，以后需要什么事先可预测，写入误差小；回合又长，读取误差大。
   - **Supersede 里完整上下文赢**（92 对 77）：问题在对话之后才出现，事先不可预测，写入误差大。
   - **Ground Truth First（2607.21962）里架构排名随历史长度反转**（96% → 72%）：两类误差随长度增长的速度不同，就一定会出现这种交叉点。
   - 这三类工作都只报告了现象，没有给出统一的机制。
2. **能事前预测，而不只是事后描述。** 在探针上测出几个参数，就能预测真实基准上哪种表示方式会赢。这类预测可以被证伪。
3. **能直接推出方法。** 理论说哪一项误差占大头，方法就针对哪一项设计（§6）。
4. **之前确认过的四个 idea 都能自然地放进来：**
   - **I3**（新旧矛盾）是读取误差里的"干扰"项；
   - **I2**（错误账本）是测量写入、读取两类误差的工具；
   - **I4**（动作时刻召回）是把读取推迟到用的那一刻、并且只读需要的部分；
   - **I1**（规模）对应一个问题：模型变强时，两类误差谁降得更快。

## 3. 误差分解框架

| 大类 | 子项 | 含义 | 去掉它的干预 | 探针上的条件 / 账本标签 |
|---|---|---|---|---|
| **写入误差** | 覆盖缺失 | schema 里没有这一项 | 动作时刻召回 | `state_noq`、`state_stale` / `stale` |
| | 写错 | 值写错了，而且之后一直错 | 带证据的写入、校验 | 模型自维护状态（待实现）/ 待定义 |
| **读取误差** | 重建 | 从长日志推当前状态推错 | 显式状态 | `raw` vs `state` / `occupied` |
| | 干扰 | 旧值和更正同时存在，用了旧的 | 作废标记、删除旧条目 | `raw` vs `tomb_tail`、`delete` / `stale`（发生在有历史的条件里） |
| | 用上失败 | 知道正确的值，但动作没用它 | 先问状态再决策，对比是否一致 | 待实现 |

**识别逻辑：** 每种干预只去掉一项误差，所以条件之间的差值就能归因到具体子项。例如：
- `raw` → `tomb_tail` 的提升 ≈ 干扰；
- `tomb_tail` → `state` 的提升 ≈ 重建；
- `state_stale` → `recall_alt` 的提升 ≈ 覆盖缺失中能被召回修复的部分。

条件的完整定义见 [algorithm_design.md](algorithm_design.md) §2。

## 4. 核心假设（每个都能单独成为一个发现）

| 编号 | 假设 | 怎么测 | 现在的初步信号 |
|---|---|---|---|
| **H1 事件数而非 token 数** | 读取误差主要由相关状态变化的次数决定，而不是上下文长度 | 探针里分开调两个旋钮：只加遥测（token 变多），或只加出入库（状态变化次数变多） | 生成器本来就把两类事件分开生成，只需加参数（[algorithm_design.md](algorithm_design.md) §1.5） |
| **H2 写入误差会粘住，读取误差是一次性的** | 状态写错后会持续错下去；从历史读错，下一步重新读时可能又对了 | 多轮闭环实验：比较"上一步错了、这一步也错"的条件概率，以及连续出错的长度分布 | 复现项目在 Sonnet 5 上看到 66 个不合 schema 的补丁，以及"补丁格式合法、但语义抄错"的情况 |
| **H3 交叉点** | 写入误差低于读取误差时状态才赢，交叉点的位置可以预测 | 同时扫描回合长度和需求可预测性，画出哪种表示方式赢的相图 | 冒烟测试里两类误差都出现了：`state_noq` 0/3；`raw` 的错误以重建为主 |
| **H4 能预测真实基准** | 用探针测出的参数，加上任务本身的统计量（状态变化次数、需求可预测性），预测真实基准上谁赢 | LongMemEval 知识更新子集、ALFWorld（注入环境变化）、LOCA | 未做 |
| **H5 规模的作用不对称** | 模型变强时读取误差下降很快，而覆盖缺失是设计问题，不随规模变化 | 3 个以上规模、2 个以上家族 | 冒烟测试里只有 Haiku 在 `raw` 上出了重建错误，Sonnet 和 Opus 没有（n=3，只看方向） |

**可以预先写好的预测**（适合做预注册）：
- 固定 token 数、增加状态变化次数时，`raw` 的准确率单调下降；
- 固定状态变化次数、增加遥测 token 时，`raw` 的准确率基本不变或只轻微下降。

## 6. 方法：自适应绑定（Adaptive Binding）

由误差分解直接推出，四个部件各对应一项误差：

| 部件 | 对应的误差 | 设计 |
|---|---|---|
| ① 尾部状态块 | 降低重建误差 | 只存可预测的字段，比如任务目标、规则涉及的关键实体；放在 prompt 末尾，不破坏历史部分的缓存 |
| ② 只追加的日志 + 作废标记 | 降低干扰，同时保证不丢信息 | 发现更正时，在末尾追加一条作废记录，不改动前面的内容 |
| ③ 动作时刻召回 | 修复覆盖缺失 | 模型先提出候选动作，再从日志里召回两类事实：候选动作本身，以及按规则排在候选前面、被它挤掉的那些选项。然后提炼成字段，让模型确认或修改 |
| ④ 写入校验 | 降低写错 | 状态更新必须引用日志里的事件编号；先执行动作、看到结果，再提交状态（修正 SKILL.state "先提交后执行"的问题） |

**召回必须覆盖被挤掉的选项**，这来自 I4 冒烟测试的发现：
- 漏掉的是**约束**（比如一条隔离通知）：只召回候选动作就能修好，0/3 → 3/3；
- 漏掉的是**机会**（比如一个更低编号的货架其实空了）：只召回候选动作完全没用（0/3），必须同时召回被挤掉的选项（3/3）。

伪代码见 [algorithm_design.md](algorithm_design.md) §5。

**消融**：逐个去掉 ①–④；召回范围分三档（只召回候选 / 候选 + 被挤掉的选项 / 全部）；提炼后召回 vs 原文召回；每步都召回 vs 只在相关实体很久没出现时才召回。

**与相近方法的区别：**
- Scroll 由模型写代码查询，但查询时机不固定；
- ContextRender 按工具结果之间的依赖关系取舍；
- PoS 只校验一致性；
- SKILL.state 直接丢弃历史。

本方法的新意落在三点上：在动作发生时取回、召回范围要覆盖候选和被挤掉的选项、对缓存友好。并且每个部件都能用错误账本验证它到底修复了哪一项误差。

## 8. 风险与兜底

**任何一个假设落空，论文都还能成立：**
- **H4 预测不准**：仍然有分解框架、缩放律和方法，降级成一篇扎实的分析加方法论文。
- **H1 不成立**（token 数也重要）：改用两因素模型，结论照样有用。
- **H5 方向相反**：本身就是一个反直觉的发现。
- **方法打不过 PoS 或 Scroll**：分析部分照样能立住，方法可以定位为"不训练、对缓存友好"的那个折中点。

**最大的风险是相邻工作出得很快。** 应对办法是分阶段推进、尽早占时间戳：

| 阶段 | 内容 | 时长 | 产出 / 检查点 |
|---|---|---|---|
| 1 | 加"事件数 vs token 数"旋钮；在 3 个以上规模上做 H1、H5 | 约 2 周 | workshop 版本。如果事件数效应和规模效应都测不出，就停下来重新评估 |
| 2 | 第 2、3 个领域；多轮闭环（H2）；交叉相图（H3） | 约 2–3 周 | — |
| 3 | 真实基准（H4）；方法和成本 | 约 3 周 | — |
| 4 | 写作 | 1–2 周 | — |

## 9. 资源需求

- **模型 API（目前最大的卡点）**：需要在云环境里配置密钥；用 Qwen 或 GPT 时，还要把对应域名加进网络白名单。详见 [research_log.md](research_log.md) §6。
- **计算量粗估**：3 个领域 × 约 7 个条件 × 4 个长度档 × 3 个更新数档 × 20 个种子，约 5000 题 / 模型，平均约 2 万 token，即每个模型约 1 亿输入 token（未计缓存）。可以先用少量种子找到每个模型开始出错的区间，再只在那附近加密采样，能省下大半。
- **GPU**：不需要。只有注意力分析和 SCR 实验才需要。
